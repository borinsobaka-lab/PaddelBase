# Размещение PaddelBase: Cloudflare + Coolify

Инструкция для агента, работающего в браузере. Порядок шагов важен: поддомен
должен резолвиться до того, как Coolify пойдёт выпускать сертификат.

Всё, что нужно сохранить и вернуть человеку, помечено **ЗАПИШИ**. Ничего из
этого нельзя оставлять только в интерфейсе — часть значений показывается один
раз.

---

## 0. Что нужно иметь на руках до старта

Если чего-то из этого нет — остановись и запроси, не придумывай:

| Что | Откуда |
| --- | --- |
| Доступ к Cloudflare с нужным доменом | у человека |
| Адрес Coolify и логин | у человека |
| **IP сервера** (тот, на котором стоит Coolify) | у человека или из Coolify → Servers |
| Строки подключения к базе, ключи Supabase | из `docs/supabase-setup.md`, шаг выполнен раньше |
| Доступ к репозиторию `borinsobaka-lab/PaddelBase` | у человека |

**Выбери поддомен и согласуй его с человеком до начала.** Дальше по тексту он
обозначен как `ПОДДОМЕН.ДОМЕН.TLD` — подставляй везде реальное значение.

---

## 1. Сгенерируй два секрета

Прямо сейчас, до всех настроек. Каждый — **не меньше 32 символов, только
латинские буквы и цифры**. Спецсимволы не бери: значения попадут в строки
подключения и в заголовки, и экранирование в интерфейсах Coolify — источник
трудноуловимых поломок.

- `SESSION_SECRET` — подпись сессионных cookie.
- `CRON_SECRET` — токен для запуска фоновых задач.

**ЗАПИШИ оба.** Восстановить их нельзя, а смена `SESSION_SECRET` разлогинит
всех.

---

## 2. Cloudflare: A-запись на поддомен

1. Войди в Cloudflare, открой нужный домен, раздел **DNS → Records**.
2. **Add record**:
   - **Type**: `A`
   - **Name**: только сам поддомен, без домена (Cloudflare допишет его сам)
   - **IPv4 address**: IP сервера с Coolify
   - **Proxy status**: **DNS only** (серое облако, не оранжевое)
   - **TTL**: `Auto`
3. Сохрани.

> **Почему серое облако.** Coolify выпустит сертификат Let's Encrypt по
> HTTP-01: сервис обращается к `http://ПОДДОМЕН.ДОМЕН.TLD/.well-known/...`
> и должен попасть на сервер. Через прокси Cloudflare проверка часто проходит,
> но при режиме SSL «Flexible» получается бесконечный редирект, а при «Full»
> без сертификата на сервере — ошибка 526. Проще выпустить сертификат
> напрямую, а прокси включить потом (шаг 9).

**Проверка перед следующим шагом.** Открой
`https://dnschecker.org/#A/ПОДДОМЕН.ДОМЕН.TLD` и убедись, что запись
резолвится в IP сервера минимум в нескольких локациях. Если нет — подожди и
проверь снова. **Не переходи к шагу 4, пока запись не резолвится:** Coolify
упрётся в неудачную проверку и попадёт в лимит Let's Encrypt (5 неудач на
домен в час).

---

## 3. Coolify: проект и источник

1. Войди в Coolify.
2. **Projects → + Add** → назови `PaddelBase` → внутри проекта окружение
   `production`.
3. **+ New Resource → Private Repository (with GitHub App)** — если приложение
   GitHub уже подключено. Если нет, используй **Public Repository** и укажи
   `https://github.com/borinsobaka-lab/PaddelBase`.
4. Выбери репозиторий `borinsobaka-lab/PaddelBase`.
5. **Branch**: спроси у человека, какую ветку выкатывать. Не подставляй
   ветку по своему усмотрению.

---

## 4. Coolify: сборка

В настройках приложения, вкладка **General**:

| Поле | Значение | Почему |
| --- | --- | --- |
| **Build Pack** | `Dockerfile` | в репозитории свой multi-stage Dockerfile |
| **Base Directory** | `/` | контекст сборки — корень репозитория |
| **Dockerfile Location** | `/apps/web/Dockerfile` | |
| **Ports Exposes** | `3000` | контейнер слушает 3000 |
| **Domains** | `https://ПОДДОМЕН.ДОМЕН.TLD` | обязательно со схемой `https://` |

**Base Directory именно `/`, а не `/apps/web`.** Dockerfile копирует
`pnpm-lock.yaml` и `packages/*` из корня монорепозитория; при контексте
`/apps/web` сборка упадёт на первом же `COPY`.

Health check, вкладка **Health Checks**:

| Поле | Значение |
| --- | --- |
| Enabled | да |
| Path | `/api/health` |
| Port | `3000` |
| Interval | `15` |
| Timeout | `10` |
| Retries | `3` |
| Start Period | `30` |

Проверка ходит в базу и отдаёт 503, если база недоступна. Это осознанно:
контейнер без базы не показывает ни одного экрана, и зелёный статус у него был
бы ложью.

---

## 5. Coolify: переменные окружения

Вкладка **Environment Variables**. Все — **runtime**, галку «Build Variable»
не ставь ни на одной: во время сборки ни база, ни ключи не нужны.

| Имя | Значение |
| --- | --- |
| `DATABASE_URL` | строка через пулер Supabase, порт **6543**, с `?pgbouncer=true&connection_limit=1` |
| `DIRECT_URL` | прямая строка Supabase, порт **5432** |
| `SESSION_SECRET` | секрет из шага 1 |
| `CRON_SECRET` | второй секрет из шага 1 |
| `SUPABASE_URL` | `https://<ref>.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role ключ |
| `SUPABASE_STORAGE_BUCKET` | `media` |

Обе строки подключения нужны и различаются не случайно: приложение работает
через пулер, а миграции пулер не переживают и идут по `DIRECT_URL`.

`SUPABASE_SERVICE_ROLE_KEY` обходит все ограничения доступа. Он должен быть
только здесь, в переменных Coolify. Не вставляй его в чат, не клади в
репозиторий, не оставляй в заметках.

Если `SUPABASE_URL` или `SUPABASE_SERVICE_ROLE_KEY` не задать, приложение
намеренно упадёт при первой загрузке фото: локальный диск в контейнере не
переживает перезапуск, и молча терять фотографии игроков хуже, чем отказать.

---

## 6. Coolify: миграции при выкатке

Вкладка **General**, поле **Pre-deployment Command**:

```
prisma migrate deploy --schema packages/db/prisma/schema.prisma
```

Команда выполняется в контейнере новой сборки до переключения трафика: если
миграция не пройдёт, старая версия останется работать.

---

## 7. Первая выкатка

1. Нажми **Deploy**.
2. Открой логи сборки и дождись окончания. Сборка монорепозитория с нуля идёт
   несколько минут.
3. Если сборка упала — **скопируй последние 40 строк лога и верни человеку**.
   Не меняй Dockerfile, не правь зависимости, не подставляй другие версии.

Когда приложение поднялось, проверь по порядку:

| Проверка | Ожидаемо |
| --- | --- |
| `https://ПОДДОМЕН.ДОМЕН.TLD/api/health` | `{"status":"ok","database":"ok",...}` |
| `https://ПОДДОМЕН.ДОМЕН.TLD/login` | экран входа, замок в адресной строке |
| Шрифт на экране входа | не системный: заголовок «PaddelBase» узкий и геометричный, цифры моноширинные |

Если health отдаёт `"database":"unreachable"` — почти наверняка неверная
`DATABASE_URL` или в Supabase не разрешены подключения. Верни человеку текст
ошибки из ответа.

Если шрифт выглядит как обычный системный — сообщи человеку: значит, в образ
не попала папка `public`. Сам ничего не правь.

---

## 8. Планировщик фоновых задач

Приложение не запускает задачи само: инстансов может быть несколько, и
внутренний планировщик отработал бы в каждом. Тик приходит снаружи.

Вкладка **Scheduled Tasks** → **+ Add**:

| Поле | Значение |
| --- | --- |
| Name | `scheduled-jobs` |
| Command | `curl -fsS -H "Authorization: Bearer $CRON_SECRET" http://127.0.0.1:3000/api/cron` |
| Frequency | `*/15 * * * *` |
| Container | контейнер приложения (единственный в списке) |

Пятнадцать минут — не произвольное число: столько же длится окно, внутри
которого задача не выполняется дважды. Более частый запуск ничего не ускорит,
более редкий сдвинет напоминания о матчах.

**Проверка.** Запусти задачу вручную кнопкой **Run** и открой её лог. Ожидаемо:

```json
{"ranMs":...,"outcomes":[{"job":"expire-open-matches","status":"OK",...},...]}
```

`SKIPPED` у всех задач — тоже успех, если ты только что запускал её: окно уже
занято. `401` означает, что `CRON_SECRET` в переменных и в команде разошлись.

---

## 9. Включить прокси Cloudflare (после того как всё работает)

Только когда шаги 7 и 8 прошли.

1. Cloudflare → **SSL/TLS → Overview** → режим **Full (strict)**.
   Именно strict: при «Flexible» получится бесконечный редирект, потому что
   Coolify сам отправляет с HTTP на HTTPS.
2. **DNS → Records** → у записи поддомена переключи Proxy status на
   **Proxied** (оранжевое облако).
3. Подожди минуту и снова открой `/api/health` и `/login`.

Если после включения прокси что-то сломалось — верни серое облако и сообщи
человеку. Это обратимо за минуту.

> **Ограничение, о котором нужно предупредить человека.** На бесплатном тарифе
> Cloudflare тело запроса ограничено 100 МБ, а приложение принимает видео
> ровно до 100 МБ. Загрузка самых больших файлов через прокси будет
> обрываться. Варианты: снизить лимит в приложении, либо оставить поддомен
> без прокси. Решение принимает человек.

---

## 10. Проверить, куда легла служебная таблица миграций

Один раз после первой успешной выкатки.

Таблицы приложения живут в схеме `app` — так их не видит PostgREST, публикующий
наружу схему `public`. Но служебную таблицу `_prisma_migrations` Prisma может
положить в `public`, и тогда она окажется доступна по публичному anon-ключу.
Содержимое безобидное (имена и контрольные суммы миграций), но отдавать наружу
структуру своих же изменений незачем.

В Supabase → **SQL Editor** выполни:

```sql
select table_schema
from information_schema.tables
where table_name = '_prisma_migrations';
```

- Ответ `app` — ничего делать не нужно.
- Ответ `public` — выполни:

```sql
alter table public._prisma_migrations enable row level security;
```

Политик не добавляй: без них таблица закрыта для anon и остаётся доступной
service_role-ключу, которым ходят миграции.

---

## 11. Что вернуть человеку

1. Адрес: `https://ПОДДОМЕН.ДОМЕН.TLD`
2. `SESSION_SECRET` и `CRON_SECRET` — **безопасным каналом, не в общем чате**.
3. Ответ `/api/health`.
4. Результат ручного запуска задачи из шага 8.
5. Схему, в которой оказалась `_prisma_migrations`, и применял ли ты RLS.
6. Статус прокси Cloudflare: включён или оставлен серым, и почему.
7. Любую ошибку, которую обошёл или не смог устранить, — дословно.

---

## Чего делать нельзя

- Не включай Cloudflare-прокси до выпуска сертификата.
- Не ставь режим SSL «Flexible».
- Не меняй файлы репозитория: Dockerfile, `next.config.mjs`, зависимости.
  Если сборка не идёт — это задача разработки, верни лог.
- Не выключай health check, чтобы «сборка позеленела».
- Не публикуй `SUPABASE_SERVICE_ROLE_KEY` и `SESSION_SECRET` нигде, кроме
  переменных окружения Coolify.
- Не подставляй ветку, домен или IP по догадке. Не знаешь — спроси.
