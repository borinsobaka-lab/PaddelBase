# Инструкция для агента: завести проект Supabase под PaddelBase

## Контекст

У заказчика **уже есть аккаунт Supabase**. Нужно создать **ещё один проект** —
не трогая существующие.

Проект используется как **управляемый PostgreSQL и файловое хранилище**, и
больше ни для чего. Supabase Auth, RLS-политики, Realtime, Edge Functions
настраивать **не нужно** — приложение ходит в базу со своего сервера через
Prisma, а авторизацию делает само.

Задача: создать проект, создать бакет для файлов и **принести обратно набор
значений** (список в конце). Ничего кроме перечисленного менять не надо.

---

## Шаг 1. Проверить тариф организации

Заказчик хочет **Pro**. Проект наследует тариф организации, поэтому:

1. Открыть организацию, в которой будет проект.
2. Посмотреть текущий тариф (Settings → Billing или бейдж рядом с названием).
3. Если организация на Free — повысить до Pro **до** создания проекта.

Если организаций несколько и непонятно, в какой создавать — **остановиться и
спросить заказчика**, не угадывать.

Почему это важно: на Free проект засыпает после недели простоя, и приложение
начинает падать, пока его не разбудят вручную. Плюс на Free файл в хранилище
ограничен 50 МБ, а приложению нужно 100 МБ.

---

## Шаг 2. Создать проект

Кнопка **New project**.

| Поле | Значение |
|---|---|
| Name | `paddelbase` |
| Database Password | сгенерировать, см. ниже |
| Region | **North EU (Stockholm)**; если такого пункта нет — **Central EU (Frankfurt)** |
| Plan | Pro |

### Пароль базы данных

Сгенерировать пароль **длиной 32 символа, только латинские буквы и цифры**.

Это не придирка: пароль подставляется внутрь строки подключения вида
`postgresql://user:ПАРОЛЬ@host:5432/postgres`. Спецсимволы (`@`, `/`, `#`, `?`,
`%`, `:`) в этой позиции требуют процентного кодирования, и любая ошибка в нём
даёт невнятную ошибку подключения, которую потом долго ищут. Буквы и цифры
снимают проблему целиком.

**Пароль сохранить** — Supabase больше его не покажет.

### Почему такой регион

Сервер приложения стоит у Hetzner в Хельсинки. Весь доступ к базе идёт
**с сервера**, а не из браузера игрока, поэтому важна задержка между Хельсинки и
регионом Supabase, а не между Тбилиси и Supabase. Стокгольм даёт около 10 мс,
Франкфурт — около 25 мс.

После нажатия **Create new project** развёртывание занимает 2–3 минуты.

## Шаг 3. Собрать строки подключения

Кнопка **Connect** в верхней панели проекта (в некоторых версиях интерфейса:
Project Settings → Database → Connection string).

Там будет несколько вариантов. Нужно скопировать **все три**:

1. **Direct connection** — хост вида `db.<project-ref>.supabase.co`, порт `5432`
2. **Transaction pooler** — хост вида `aws-N-<регион>.pooler.supabase.com`, порт `6543`
3. **Session pooler** — тот же хост пулера, порт `5432`

Копировать в режиме **URI** (не psql, не Golang и т. п.).

Строки содержат `[YOUR-PASSWORD]` вместо пароля — **так и прислать, не
подставляя пароль**. Пароль придёт отдельным полем.

**Все три нужны обязательно.** Прямое подключение у Supabase работает только по
IPv6, и если на сервере Hetzner IPv6 не поднят, миграции по нему не пойдут — их
придётся пустить через session pooler. Какой вариант использовать, решится при
настройке сервера, но собрать надо сразу, чтобы не возвращаться.

Если рядом с каким-то из вариантов написано, что он недоступен или требует
платного дополнения (IPv4 add-on) — **отметить это в отчёте**.

---

## Шаг 4. Собрать ключи API

Project Settings → **API Keys** (в старых версиях — Project Settings → API).

Нужно:

1. **Project URL** — вида `https://<project-ref>.supabase.co`
2. **Секретный серверный ключ**. В зависимости от версии интерфейса это либо:
   - новый ключ вида `sb_secret_...` (раздел «Secret keys»), **либо**
   - старый ключ `service_role` (раздел «Legacy API keys», длинная строка JWT).

   Прислать тот, что есть, и **обязательно указать, какой именно из двух**.
   Если есть оба — прислать новый `sb_secret_...`.

Публичный ключ (`anon` / `publishable`) приложению не нужен, присылать не надо.

---

## Шаг 5. Создать бакет для файлов

Раздел **Storage** → **New bucket**.

| Параметр | Значение |
|---|---|
| Name | `media` |
| Public bucket | **включить** |
| File size limit | `100 MB` |
| Allowed MIME types | `image/jpeg, image/png, image/webp, video/mp4, video/quicktime` |

Про публичность: приложение отдаёт фотографии в ленте по прямым ссылкам, без
подписи. Это осознанный выбор для ленты комьюнити — снимки с корта не
приватные данные. Если бакет сделать приватным, ссылки перестанут открываться.

Если поле лимита не даёт поставить 100 МБ — **записать, какой максимум
разрешён**, и сообщить.

---

## Шаг 6. Проверить, какие схемы открыты наружу

Project Settings → API → **Exposed schemas** (или Data API → Exposed schemas).

Там должно быть **только** `public` и `graphql_public`.

**Ничего не добавлять.** Просто подтвердить в отчёте, что список именно такой.

Причина: таблицы приложения будут созданы в отдельной схеме `app` именно для
того, чтобы автоматический REST-интерфейс Supabase их не видел. Если добавить
`app` в этот список, вся база станет читаемой снаружи по публичному ключу.

---

## Чего делать НЕ надо

- **Не включать провайдеров** в разделе Authentication. Supabase Auth не
  используется.
- **Не создавать таблицы** в SQL Editor. Схему создаст миграция приложения.
- **Не добавлять схему `app`** в Exposed schemas (см. шаг 6).
- **Не включать Network Restrictions** сейчас. Их настроим позже, когда будет
  известен IP-адрес сервера, — иначе есть риск закрыть доступ самим себе.
- **Не трогать другие проекты** в аккаунте.

```
ПРОЕКТ
  Организация:            
  Название проекта:       
  Project ref:            
  Регион:                 
  Тариф:                  

ПАРОЛЬ БАЗЫ ДАННЫХ
  Пароль:                 

СТРОКИ ПОДКЛЮЧЕНИЯ (как есть, с [YOUR-PASSWORD])
  Direct connection:      
  Transaction pooler:     
  Session pooler:         
  Примечания (что-то недоступно / требует IPv4 add-on):

КЛЮЧИ
  Project URL:            
  Секретный ключ:         
  Тип ключа:              sb_secret_... / legacy service_role

ХРАНИЛИЩЕ
  Бакет создан:           да / нет
  Имя бакета:             media

ПРОВЕРКИ

  Authentication:         провайдеры не включались, подтверждаю / включены такие-то
```

## Безопасность

Секретный ключ Supabase **обходит все ограничения доступа** — он равносилен
полному доступу к базе и хранилищу. Пароль базы — тоже.

Отсюда два следствия:

1. Переписку с агентом, где эти значения прозвучали, дальше считать секретной:
   не пересылать, не публиковать, не оставлять в общих чатах.
2. Если она где-то сохраняется или доступна кому-то ещё — **после настройки
   ротировать**: пароль в Project Settings → Database → Reset database
   password, ключ — в API Keys.

Значения нужны один раз: они попадут в переменные окружения Coolify на сервере,
и больше нигде храниться не будут.

## Куда это пойдёт дальше (для понимания, делать не нужно)

Полученные значения превратятся в конфигурацию приложения примерно так:

```
DATABASE_URL   = transaction pooler + ?pgbouncer=true&connection_limit=1
DIRECT_URL     = direct connection либо session pooler (решится по IPv6 на сервере)
SUPABASE_URL   = Project URL
SUPABASE_SERVICE_ROLE_KEY = секретный ключ
SUPABASE_STORAGE_BUCKET   = media
```

После этого на базе будет выполнена миграция, которая создаст схему `app` и все
таблицы приложения.
